# Как участвовать в разработке

Здесь описано, как запустить «Воздушный шар», проверить изменения и оформить их так, чтобы остальным было легко их принять.

## Структура репозитория

| Каталог | Что внутри |
| --- | --- |
| `backend/` | Spring Boot 3.3 на Java 21. Пакеты: `api` — REST-контроллеры, `application` — игровой цикл, рейтинг и лотерея, `domain` — математическая модель и настройки темы, `auth` — аккаунты и сессии, `rounds` и `tournament` — хранение раундов и турнира, `daily` — ежедневный пазл |
| `backend/src/main/resources/` | `application.yml`, справочный снимок настроек `game-config.yml`, контракт API `static/openapi.yaml` |
| `frontend/` | React 18, TypeScript и Vite: экраны в `src/features`, API-клиент и игровой движок в `src/shared`, стили в `src/styles.css` |
| `infra/` | `docker-compose.yml` для запуска всего стека |
| `docs/` | архитектура и экономика коэффициентов |

## Запуск

Весь стек — frontend, backend и база:

```bash
docker compose -f infra/docker-compose.yml up --build
```

Приложение — <http://localhost:3000>, API — <http://localhost:8080/api/v1>, Swagger UI — <http://localhost:3000/swagger-ui/index.html>. Демо-доступы указаны в README.

Без Docker нужны Java 21 с Gradle и Node.js 22. В одном терминале:

```bash
cd backend && gradle bootRun
```

В другом:

```bash
cd frontend && npm install && npm run dev
```

Vite слушает порт `5173` и проксирует `/api` и Swagger UI на `localhost:8080`.

## Проверка перед коммитом

- **Backend:** `gradle test` в каталоге `backend`. Если локально нет Java 21, тесты запускаются в контейнере из корня репозитория:

  ```bash
  docker run --rm -v "$PWD/backend:/src:ro" -v balloon-gradle-cache:/home/gradle/.gradle gradle:8.10-jdk21 bash -c "cp -r /src /workspace && cd /workspace && gradle --no-daemon test --console=plain"
  ```

  В Git Bash на Windows добавьте перед командой `MSYS_NO_PATHCONV=1` и укажите путь к `backend` в формате `C:\\...`.
- **Frontend:** `npm run build` в каталоге `frontend` — проверка типов TypeScript и сборка.
- **Сценарии:** изменения игрового цикла проверьте вручную по обязательным сценариям — ставка и запуск, cashout, crash, бустер, смена параметров. Серверные операции удобно проверять в Swagger UI или запросами из раздела API в README.

Тест `ModelsOddsTest` держит возврат игроку в коридоре 95–97% для всех вариантов ставки и уровней. Если меняете шансы или коэффициенты, подтвердите новую экономику расчётом или серией запусков, а не одним случайным раундом.

## Правила изменений

- **Сервер — источник правды.** Случайность, коэффициенты, выплаты и очки считаются только на backend; клиент показывает состояние и отправляет команды.
- **Документация вместе с кодом.** Меняете механику, настройки или API — обновите в том же изменении README, `docs/` и `backend/src/main/resources/static/openapi.yaml`.
- **Комментарии** объясняют правило или причину решения, а не пересказывают код. Пишите в стиле соседнего кода.
- **Секреты** не попадают в репозиторий: пароли, токены и ключи передаются через переменные окружения.
- **Сообщение коммита** пишется по-русски и говорит, что изменилось для игрока или разработчика, например «Раунды и турнир хранятся в базе».

## Ветки и публикация

Основная ветка — `master`. Крупные изменения делайте в отдельной ветке и сливайте после проверки. Команда ведёт репозиторий на GitHub, репозиторий для сдачи решения — на GitVerse; изменения публикуются в оба.

## Ошибки, идеи и уязвимости

Ошибки и предложения оформляйте в issue: шаги воспроизведения, ожидаемый и фактический результат. Об уязвимостях не пишите в публичных issue — порядок описан в [SECURITY.md](SECURITY.md). Участвуя в проекте, вы соглашаетесь с [правилами поведения](CODE_OF_CONDUCT.md).
