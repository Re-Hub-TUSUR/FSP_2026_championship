# «Воздушный шар»

Прототип игры с серверной случайностью: Java 21 / Spring Boot API, React-клиент, H2 file database. При подключённом backend сервер — авторитетный источник состояния раунда; браузер отображает состояние и отправляет команды `start` / `cashout`. PostgreSQL и Redis подняты в Compose как задел на production-этап, приложение их пока не использует.

## Быстрый запуск

Требуются Docker Desktop с Compose v2. Из корня репозитория:

```bash
docker compose -f infra/docker-compose.yml up --build
```

Поднимаются четыре сервиса: `frontend` (nginx), `backend`, `postgres`, `redis`.

- приложение: <http://localhost:3000>
- API: <http://localhost:8080/api/v1>
- демо-доступы: игрок `demo` / `demo123`, администратор `admin` / `admin123`

Единая точка входа в клиенте — <http://localhost:3000/> (или `http://localhost:5173/` при запуске Vite). Авторизация открывается модальным окном на landing-странице; старые адреса `/login` и `/register` автоматически перенаправляются на `/`, чтобы не было двух разных экранов входа.

Аккаунты, роли, баланс, очки, журнал действий и опубликованные настройки игры сохраняются в H2 file database (volume `backend-data`) и переживают перезапуск. Раунды живут в памяти сервиса: публичная история удерживает до 200 завершённых раундов текущего процесса и теряется при перезапуске backend.

## Что умеет прототип

- **Аккаунты и роли.** Регистрация, вход по непрозрачному токену сессии, роли `USER` и `ADMIN`. Старт, cashout, профиль, ежедневный бонус и лотерея требуют авторизации; админские запросы — роли `ADMIN`.
- **Игра.** Две темы (красная и зелёная), четыре варианта ставки с бустером, лента коэффициентов прошлых игр, полёт по уровням, cashout с продолжением полёта, автоматическая выплата на вершине, фрагмент ежедневного пазла по итогам раунда.
- **История раундов.** Сводка (число раундов, доля побед, лучший коэффициент, итог) и таблица по каждому полёту с уровнем взрыва.
- **Рейтинг.** Таблица участников с поиском и сортировкой; данные обновляются REST-запросом, а не WebSocket.
- **Административная панель.** Управление параметрами игры, пользователями и журналом действий — доступна только роли `ADMIN`.

Состояние раунда, proof, cashout, а также получение и принятие персонального предложения лотереи доступны только авторизованному владельцу раунда; отсутствие сессии возвращает 401, а чужой или неизвестный идентификатор скрывается ответом 404. История и лента crash остаются общей публичной лентой.

## Механика раунда

Шар проходит по одному уровню в секунду. На каждом уровне он проходит проверку на разрыв: шанс взрыва растёт экспоненциально вместе с высотой, а коэффициент выплаты обратен вероятности до этого уровня долететь.

```
hazard(L)     = min(maxHazard, baseHazard × hazardGrowth^(L-1))
survival(L)   = Π (1 - hazard(i)), i = 1..L
multiplier(L) = rtp / survival(L)
```

Из-за этого коэффициенты не статические, а ускоряются: для красной темы ×1.09 → ×25.54 за 12 уровней при шансе взрыва от 12% до 40%. Значение rtp=0.96 является ориентиром базовой лестницы до округления; пользовательские ручные лестницы и бустеры могут изменить фактический возврат.

Взрыв определяется детерминированно из сида раунда: шар лопается на первом уровне, где `HMAC_SHA256(seed, roundId:level) < hazard(level)`. До начала раунда сервер публикует `commitment = sha256(seed:roundId:configVersion)`, а после завершения отдаёт сид и уровень взрыва в `GET /rounds/{id}/proof` — результат можно проверить самостоятельно.

Ставка списывается при старте раунда. Нажатие «Забрать» фиксирует коэффициент и выплату, но полёт продолжается: шар летит до точки взрыва, и только после этого открывается экран результата с сообщением о потенциальном максимуме. Базовые очки за уровни продолжают начисляться до фактического окончания полёта, даже после cashout; бустер после cashout не активируется. Если шар долетел до последнего уровня без cashout, выплата начисляется автоматически.

### Бустеры

Бустер ждёт на случайном уровне и, если шар долетает до него раньше cashout, умножает коэффициент и начисляет дополнительные очки. После нажатия «Забрать» бустер не срабатывает.

Для тира с множителем B backend использует шанс появления `min(1, BOOSTER_BUDGET / (B - 1))` при `BOOSTER_BUDGET = 0.5`: примерно 50% для ×2, 25% для ×3 и 16,7% для ×4. Если бустер появился, его уровень выбирается по нормированным весам уровней.

Для варианта с бустером базовая лестница заранее уменьшается на ожидаемый вклад:

```
priced(L) = round2(base(L) / (1 + BOOSTER_BUDGET × cumulativeWeight(L)))
```

При достижении boosterLevel до cashout backend умножает действующий коэффициент на B и добавляет `pointsBoosterBonus × B` к игровым очкам. Поэтому в текущей реализации бустер влияет и на выплату, и на очки; из-за округления и пользовательских настроек фактический RTP может отличаться от ориентира.

### Ежедневный пазл и билет

По итогам каждого раунда — выигранного или проигранного — игрок получает случайный недостающий фрагмент пазла текущего календарного дня. Пазл состоит из шести фрагментов; после 6/6 открывается один лотерейный билет. Стирание билета выполняется через `POST /daily-bonus/claim`: сервер атомарно выбирает целую награду от 10 до 2 000 бонусов и начисляет её на баланс. Вероятность джекпота 2 000 — ровно 0,001%; повторный запрос не начисляет награду повторно. Прогресс находится в панели под балансом и в профиле, результат последнего фрагмента — на экране раунда.

### Закрепи успех (лотерейные билеты)

Модуль апсейла из п. 1.8. После раунда, в котором игрок забрал выигрыш не меньше `minWinAmount` (по умолчанию 50 ★), показывается персональное предложение купить лотерейные билеты со скидкой 20%. Количество билетов растёт вместе с выигрышем (`выигрыш / 25`, максимум 10) и урезается до доступного баланса, цена пересчитывается на сервере при покупке. Окно закрывается само через `popupTimeout` секунд (по умолчанию 10); `minWinAmount` и `popupTimeout` меняются в административной панели.

Чтобы предложение не раздражало повторами, сервер считает выигрыши игрока в профиле и помечает подходящим каждый четвёртый (`LotteryService.OFFER_EVERY_WINS`). Счётчик выигрышей сохраняется в H2, но сам раунд и признак принятого предложения находятся в памяти `GameService`; после перезапуска backend старые предложения по раундам недоступны.

Те же билеты продаются наборами во вкладке «Лотерея», остаток билетов виден в шапке рядом с балансом. Покупка имитируется: списываются бонусные баллы, начисляются билеты.

## Административная панель

Открывается по ссылке «Админ» в шапке под ролью `ADMIN`; игрока прямой переход на `/admin` возвращает в игру, а `/api/v1/admin/*` отвечает `403`. Панель закрывает группы настроек из п. 1.9 постановки задачи:

| Группа | Что меняется |
| --- | --- |
| Базовые | `gameId`, название, тип игры, флаг «тема доступна игрокам» |
| Апсейл | `minWinAmount` — порог выигрыша для предложения, `popupTimeout` — автозакрытие окна |
| Математическая модель | фиксированное число уровней для темы (RED — 12, GREEN — 9), `baseHazard`, `hazardGrowth`, `maxHazard`, `rtp` |
| Коэффициенты уровней | лестница по формуле либо заданные вручную значения для каждого уровня |
| Положение бустера | вероятность выпадения бустера на каждом уровне (`line_N_loot_prob`) |
| Множители бустеров | четыре тира: размер ставки и множитель очков |
| Начисление очков | очки за уровень, бонус за cashout, бонус за бустер |

Значения проверяются на сервере: возрастающая лестница, неверное число коэффициентов, уровни вне диапазона, `rtp` вне `0.5…1.0`, отрицательные очки отклоняются с `400` и понятным сообщением. Рядом с каждым уровнем панель показывает ожидаемый возврат (`шанс долететь × коэффициент`) — значения выше 100% подсвечиваются, то есть конфигурация играет в минус для платформы.

Изменения применяются к новым раундам сразу; запущенные раунды доигрывают по snapshot конфигурации, с которым стартовали. Снятие флага «тема доступна игрокам» отклоняет старт новых раундов по этой теме. Кнопка сброса возвращает тему к значениям по умолчанию.

Настройки хранятся в таблице `game_config` и поднимаются при старте сервиса, поэтому переживают перезапуск контейнера.

## Конфигурация игры

Значения по умолчанию заданы в `Config.defaults` (`backend/src/main/java/com/example/balloon/domain/Models.java`), их справочный снимок — в `backend/src/main/resources/game-config.yml`. Штатный способ менять параметры — административная панель либо `PUT /api/v1/admin/config?theme=RED` с токеном администратора.

Кнопка демо-пополнения вызывает `POST /api/v1/auth/topup`: сервер добавляет ровно 500 бонусов авторизованному аккаунту не чаще одного раза за календарный день в зоне Europe/Moscow. Повтор до следующего дня возвращает бизнес-ошибку `400`.

## API

Все маршруты используют префикс `/api/v1`. Авторизованные запросы передают `Authorization: Bearer <token>`, где token — непрозрачная серверная сессия, а не JWT. Для запуска раунда можно передать уникальный `Idempotency-Key` в заголовке или теле: ключ не должен содержать пробельные символы и не должен быть длиннее 128 символов. Повтор с тем же ключом и теми же параметрами возвращает исходный раунд, а с другими параметрами получает `400`. Без ключа повторный запрос создаёт новый раунд.

```bash
TOKEN=$(curl -s -X POST http://localhost:8080/api/v1/auth/login \
  -H "Content-Type: application/json" \
  -d '{"username":"demo","password":"demo123"}' | jq -r .token)

curl http://localhost:8080/api/v1/me -H "Authorization: Bearer $TOKEN"

curl -X POST http://localhost:8080/api/v1/rounds \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: demo-$(date +%s)" \
  -d '{"theme":"RED","betOptionId":"red-x2"}'

curl -X POST http://localhost:8080/api/v1/rounds/<ROUND_ID>/cashout \
  -H "Authorization: Bearer $TOKEN"
```

Основные маршруты:

| Метод | Путь | Назначение |
| --- | --- | --- |
| `POST` | `/auth/register`, `/auth/login`, `/auth/logout` | Аккаунты и сессии |
| `POST` | `/auth/topup` | Авторизованное демо-пополнение баланса на 500 бонусов (не более одного раза в календарный день по Europe/Moscow) |
| `GET` | `/me` | Профиль, баланс, роль и состояние ежедневного пазла |
| `GET` | `/daily-bonus` | Состояние пазла и лотерейного билета за текущий день |
| `POST` | `/daily-bonus/claim` (`/scratch`) | Стереть билет и получить награду один раз за день |
| `GET` | `/game/config?theme=RED\|GREEN` | Публичные параметры темы и лестница коэффициентов |
| `POST` | `/rounds`, `/rounds/{id}/cashout` | Старт раунда и cashout (Bearer; cashout только владелец, чужой/неизвестный ID — `404`) |
| `GET` | `/rounds/{id}`, `/rounds/{id}/proof` | Состояние и проверка честности собственного раунда (Bearer + владелец; чужой/неизвестный ID — `404`) |
| `GET` | `/rounds/history` | Общая публичная обезличенная история завершённых раундов |
| `GET` | `/leaderboard` | Рейтинг участников |
| `GET` | `/tournament` | Текущий турнир: срок, статус и призы для топ-3 |
| `GET`/`POST` | `/lottery`, `/lottery/buy` | Каталог билетов и покупка набора |
| `GET`/`POST` | `/lottery/offer/{roundId}`, `/lottery/offer/accept` | Персональное предложение «Закрепи успех» и его покупка (Bearer + владелец; чужой/неизвестный ID — `404`) |
| `GET`/`PUT` | `/admin/config` | Чтение и публикация настроек темы (только `ADMIN`) |
| `POST` | `/admin/config/reset` | Сброс темы к значениям по умолчанию |
| `GET`/`POST`/`PUT` | `/admin/users`, `/admin/users/{id}/block`, `/admin/users/{id}/adjust`, `/admin/audit` | Управление пользователями и журнал |

Контракт с моделями ответов — в [docs/api/openapi.yaml](docs/api/openapi.yaml). Realtime реализован опросом: клиент запрашивает `GET /rounds/{id}` раз в 600 мс, что укладывается в требование обновления не реже раза в секунду. WebSocket/STOMP endpoint `/ws` в текущем backend не реализован и не подключён.

## Изменения относительно первой версии

- **Экономика.** Ставка списывается при старте, выплата начисляется при cashout и автоматически при достижении вершины (раньше долетевший до верха раунд закрывался с нулевой выплатой). Баланс в шапке обновляется сразу после раунда.
- **История раундов.** Появилась сводка и таблица с уровнем, коэффициентом, итогом и уровнем взрыва.
- **Модель случайности.** Вместо предрассчитанной точки crash с линейным ростом — проверка на разрыв на каждом уровне с экспоненциально растущим шансом, провably fair через commitment и раскрытие сида.
- **Коэффициенты.** Лестница считается от вероятности выживания и растёт экспоненциально; rtp — ориентир до округления, а тировая лестница учитывает ожидаемый вклад бустера.
- **Аккаунты и роли.** Регистрация, вход, роли `USER`/`ADMIN`, блокировка и корректировка баланса, журнал действий.
- **Рейтинг и профиль.** REST-таблица участников с поиском и сортировкой и страница профиля.
- **Административная панель.** Управление реализованными параметрами игры с серверной валидацией, предпросмотром лестницы и сохранением настроек в H2.
- **Игровой цикл по постановке.** Лента «Прошлые игры» на экранах ставки и полёта, блокировка ставок дороже баланса, правила по кнопке до подтверждения ставки, продолжение полёта после cashout с сообщением «Могли бы забрать больше», автоматический возврат к выбору ставки через 10 секунд, бустер с умножением коэффициента и дополнительными очками. Фрагмент пазла выдаётся отдельно после завершения раунда.
- **Хранение.** Аккаунты и настройки игры перенесены в H2 file database на volume `backend-data`.

## Локальная разработка без Docker

Нужны Java 21 с Gradle для `backend` и Node.js 22 для `frontend`. Внешние базы не требуются: используется H2 в файле `backend/data/balloon`.

```bash
# terminal 1
cd backend
gradle bootRun

# terminal 2
cd frontend
npm install
npm run dev
```

Vite слушает `5173` и проксирует `/api` на `localhost:8080`. Локальный демо-режим на localStorage включается только явно через `VITE_DEMO_MODE=true`; сам по себе недоступный или ошибочный backend больше не подменяется локальной транзакцией. Демо-режим предназначен только для разработки интерфейса и не удовлетворяет проверке серверной случайности, авторизации или админ-панели.

## Остановка и очистка

```bash
docker compose -f infra/docker-compose.yml down
```

```bash
# удалить данные: H2-аккаунты и настройки, а также тома PostgreSQL/Redis
docker compose -f infra/docker-compose.yml down -v
```

После удаления тома `backend-data` аккаунты `demo` и `admin` создаются заново при следующем старте.
