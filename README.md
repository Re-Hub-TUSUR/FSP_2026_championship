# «Воздушный шар»

Прототип игры с серверной случайностью: Java 21 / Spring Boot API, React-клиент, H2 file database. Сервер — авторитетный источник состояния раунда; браузер только отображает состояние и отправляет команды `start` / `cashout`. PostgreSQL и Redis подняты в Compose как задел на production-этап, приложение их пока не использует.

## Быстрый запуск

Требуются Docker Desktop с Compose v2. Из корня репозитория:

```bash
docker compose -f infra/docker-compose.yml up --build
```

Поднимаются четыре сервиса: `frontend` (nginx), `backend`, `postgres`, `redis`.

- приложение: <http://localhost:3000>
- API: <http://localhost:8080/api/v1>
- демо-доступы: игрок `demo` / `demo123`, администратор `admin` / `admin123`

Единая точка входа в клиенте — <http://localhost:3000/> (или `http://localhost:5173/` при запуске Vite). Авторизация открывается модальным окном на landing-странице; старые адреса `/login` и `/register` автоматически перенаправляются на `/`, чтобы не было двух разных экранов входа.

Аккаунты, роли, баланс, очки, журнал действий и опубликованные настройки игры сохраняются в H2 file database (volume `backend-data`) и переживают перезапуск. Раунды живут в памяти сервиса — хранятся последние 200.

## Что умеет прототип

- **Аккаунты и роли.** Регистрация, вход по токену, роли `USER` и `ADMIN`. Игровые запросы требуют авторизации, админские — роли `ADMIN`.
- **Игра.** Две темы (красная и зелёная), четыре варианта ставки с бустером, лента коэффициентов прошлых игр, полёт по уровням, cashout с продолжением полёта, автоматическая выплата на вершине, фрагмент ежедневного пазла по итогам раунда.
- **История раундов.** Сводка (число раундов, доля побед, лучший коэффициент, итог) и таблица по каждому полёту с уровнем взрыва.
- **Рейтинг.** Live-таблица участников с поиском и сортировкой.
- **Административная панель.** Управление параметрами игры, пользователями и журналом действий — доступна только роли `ADMIN`.

## Механика раунда

Шар проходит по одному уровню в секунду. На каждом уровне он проходит проверку на разрыв: шанс взрыва растёт экспоненциально вместе с высотой, а коэффициент выплаты обратен вероятности до этого уровня долететь.

```
hazard(L)     = min(maxHazard, baseHazard × hazardGrowth^(L-1))
survival(L)   = Π (1 - hazard(i)), i = 1..L
multiplier(L) = rtp / survival(L)
```

Из-за этого коэффициенты не статические, а ускоряются: для красной темы ×1.09 → ×25.54 за 12 уровней при шансе взрыва от 12% до 40%. Возврат игроку одинаков на любом уровне (~96%), поэтому ни одна стратегия выхода не выгоднее другой.

Взрыв определяется детерминированно из сида раунда: шар лопается на первом уровне, где `HMAC_SHA256(seed, roundId:level) < hazard(level)`. До начала раунда сервер публикует `commitment = sha256(seed:roundId:configVersion)`, а после завершения отдаёт сид и уровень взрыва в `GET /rounds/{id}/proof` — результат можно проверить самостоятельно.

Ставка списывается при старте раунда. Нажатие «Забрать» фиксирует коэффициент и выплату, но полёт продолжается: шар летит до точки взрыва, и только после этого открывается экран результата с сообщением о потенциальном максимуме. Если шар долетел до последнего уровня без cashout, выплата начисляется автоматически.

### Бустеры

Бустер ждёт на случайном уровне и, если шар долетает до него раньше cashout, умножает коэффициент и начисляет дополнительные очки. После нажатия «Забрать» бустер не срабатывает.

Чтобы сильный бустер не ломал экономику, его ожидаемый вклад одинаков для всех вариантов ставки:

```
шанс появления(множитель) = BOOSTER_BUDGET / (множитель - 1)
коэффициент(L)            = базовый(L) / (1 + BOOSTER_BUDGET × доля уровней до L)
```

При `BOOSTER_BUDGET = 0.5` бустер ×2 выпадает в 50% раундов, ×3 — в 25%, ×4 — в 17%. Базовые коэффициенты ставок с бустером ниже ровно на ожидаемый вклад, поэтому возврат игроку остаётся ~96% для любого тира — проверено серией из 300 000 симуляций на каждый уровень выхода.

### Ежедневный пазл и билет

По итогам каждого раунда — выигранного или проигранного — игрок получает случайный недостающий фрагмент пазла текущего календарного дня. Пазл состоит из шести фрагментов; после 6/6 открывается один лотерейный билет. Стирание билета выполняется через `POST /daily-bonus/claim`: сервер атомарно выбирает целую награду от 10 до 2 000 бонусов и начисляет её на баланс. Вероятность джекпота 2 000 — ровно 0,001%; повторный запрос не начисляет награду повторно. Прогресс находится в панели под балансом и в профиле, результат последнего фрагмента — на экране раунда.

## Административная панель

Открывается по ссылке «Админ» в шапке под ролью `ADMIN`; игрока прямой переход на `/admin` возвращает в игру, а `/api/v1/admin/*` отвечает `403`. Панель закрывает группы настроек из п. 1.9 постановки задачи:

| Группа | Что меняется |
| --- | --- |
| Базовые | `gameId`, название, тип игры, флаг «тема доступна игрокам» |
| Математическая модель | количество уровней (3…30), `baseHazard`, `hazardGrowth`, `maxHazard`, `rtp` |
| Коэффициенты уровней | лестница по формуле либо заданные вручную значения для каждого уровня |
| Положение бустера | вероятность выпадения бустера на каждом уровне (`line_N_loot_prob`) |
| Множители бустеров | четыре тира: размер ставки и множитель очков |
| Начисление очков | очки за уровень, бонус за cashout, бонус за бустер |

Значения проверяются на сервере: убывающая лестница, неверное число коэффициентов, уровни вне диапазона, `rtp` вне `0.5…1.0`, отрицательные очки отклоняются с `400` и понятным сообщением. Рядом с каждым уровнем панель показывает ожидаемый возврат (`шанс долететь × коэффициент`) — значения выше 100% подсвечиваются, то есть конфигурация играет в минус для платформы.

Изменения применяются к новым раундам сразу; запущенные раунды доигрывают по snapshot конфигурации, с которым стартовали. Снятие флага «тема доступна игрокам» отклоняет старт новых раундов по этой теме. Кнопка сброса возвращает тему к значениям по умолчанию.

Настройки хранятся в таблице `game_config` и поднимаются при старте сервиса, поэтому переживают перезапуск контейнера.

## Конфигурация игры

Значения по умолчанию заданы в `Config.defaults` (`backend/src/main/java/com/example/balloon/domain/Models.java`), их справочный снимок — в `backend/src/main/resources/game-config.yml`. Штатный способ менять параметры — административная панель либо `PUT /api/v1/admin/config?theme=RED` с токеном администратора.

## API

Все маршруты используют префикс `/api/v1`. Авторизованные запросы передают `Authorization: Bearer <token>`. Для запуска раунда рекомендуется уникальный `Idempotency-Key`.

```bash
TOKEN=$(curl -s -X POST http://localhost:8080/api/v1/auth/login \
  -H "Content-Type: application/json" \
  -d '{"username":"demo","password":"demo123"}' | jq -r .token)

curl http://localhost:8080/api/v1/me -H "Authorization: Bearer $TOKEN"

curl -X POST http://localhost:8080/api/v1/rounds \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: demo-$(date +%s)" \
  -d '{"theme":"RED","betOptionId":"red-x2"}'

curl -X POST http://localhost:8080/api/v1/rounds/<ROUND_ID>/cashout \
  -H "Authorization: Bearer $TOKEN"
```

Основные маршруты:

| Метод | Путь | Назначение |
| --- | --- | --- |
| `POST` | `/auth/register`, `/auth/login`, `/auth/logout` | Аккаунты и сессии |
| `GET` | `/me` | Профиль, баланс, роль и состояние ежедневного пазла |
| `GET` | `/daily-bonus` | Состояние пазла и лотерейного билета за текущий день |
| `POST` | `/daily-bonus/claim` (`/scratch`) | Стереть билет и получить награду один раз за день |
| `GET` | `/game/config?theme=RED\|GREEN` | Публичные параметры темы и лестница коэффициентов |
| `POST` | `/rounds`, `/rounds/{id}/cashout` | Старт раунда и cashout |
| `GET` | `/rounds/{id}`, `/rounds/history`, `/rounds/{id}/proof` | Состояние, история, проверка честности |
| `GET` | `/leaderboard` | Рейтинг участников |
| `GET`/`PUT` | `/admin/config` | Чтение и публикация настроек темы (только `ADMIN`) |
| `POST` | `/admin/config/reset` | Сброс темы к значениям по умолчанию |
| `GET`/`POST`/`PUT` | `/admin/users`, `/admin/users/{id}/block`, `/admin/users/{id}/adjust`, `/admin/audit` | Управление пользователями и журнал |

Контракт с моделями ответов — в [docs/api/openapi.yaml](docs/api/openapi.yaml). Realtime реализован опросом: клиент запрашивает `GET /rounds/{id}` раз в 600 мс, что укладывается в требование обновления не реже раза в секунду. WebSocket STOMP `/ws` заложен в архитектуре как следующий шаг и пока не включён.

## Изменения относительно первой версии

- **Экономика.** Ставка списывается при старте, выплата начисляется при cashout и автоматически при достижении вершины (раньше долетевший до верха раунд закрывался с нулевой выплатой). Баланс в шапке обновляется сразу после раунда.
- **История раундов.** Появилась сводка и таблица с уровнем, коэффициентом, итогом и уровнем взрыва.
- **Модель случайности.** Вместо предрассчитанной точки crash с линейным ростом — проверка на разрыв на каждом уровне с экспоненциально растущим шансом, провably fair через commitment и раскрытие сида.
- **Коэффициенты.** Лестница считается от вероятности выживания, растёт экспоненциально и даёт одинаковый возврат игроку на любом уровне.
- **Аккаунты и роли.** Регистрация, вход, роли `USER`/`ADMIN`, блокировка и корректировка баланса, журнал действий.
- **Рейтинг и профиль.** Live-таблица участников и страница профиля.
- **Административная панель.** Полное управление параметрами игры по п. 1.9 с серверной валидацией, предпросмотром лестницы и сохранением настроек в базу.
- **Игровой цикл по постановке.** Лента «Прошлые игры» на экранах ставки и полёта, блокировка ставок дороже баланса, правила по кнопке до подтверждения ставки, продолжение полёта после cashout с сообщением «Могли бы забрать больше», автоматический возврат к выбору ставки через 10 секунд, бустер с умножением коэффициента и наградой-фрагментом.
- **Хранение.** Аккаунты и настройки игры перенесены в H2 file database на volume `backend-data`.

## Локальная разработка без Docker

Нужны Java 21 с Gradle для `backend` и Node.js 22 для `frontend`. Внешние базы не требуются: используется H2 в файле `backend/data/balloon`.

```bash
# terminal 1
cd backend
gradle bootRun

# terminal 2
cd frontend
npm install
npm run dev
```

Vite слушает `5173` и проксирует `/api` на `localhost:8080`. Если backend не запущен, клиент переходит в демо-режим на localStorage — удобно для правки интерфейса, но авторизация и админ-панель в этом режиме недоступны.

## Остановка и очистка

```bash
docker compose -f infra/docker-compose.yml down
```

```bash
# удалить данные: аккаунты, настройки игры, тома PostgreSQL/Redis
docker compose -f infra/docker-compose.yml down -v
```

После удаления тома `backend-data` аккаунты `demo` и `admin` создаются заново при следующем старте.
